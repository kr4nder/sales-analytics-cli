# Аналитика продаж (CLI, .NET 10)

Консольное приложение: читает CSV с продажами, считает аналитику и выводит её в консоль
либо сохраняет в JSON. Тестовое задание, исходная постановка — в [`Readme.rst`](Readme.rst).

## Сборка и запуск

Нужен только .NET SDK 10.

```bash
dotnet build
dotnet test

dotnet run --project src/SalesAnalytics.Cli -- --mode=console --input=sales_5000.csv
dotnet run --project src/SalesAnalytics.Cli -- --mode=file --input=sales_5000.csv --output=result.json
```

`--` отделяет аргументы приложения от аргументов SDK. Собранный exe вызывается напрямую:

```bash
SalesAnalytics.Cli --mode=full --input=sales_5000.csv --output=result.json
```

## Аргументы

| Аргумент | Кратко | Описание |
| --- | --- | --- |
| `--mode` | `-m` | Режим работы, по умолчанию `console` |
| `--input` | `-i` | Путь к CSV. Обязательный |
| `--output` | `-o` | Путь к JSON. Без него отчёт идёт в консоль |
| `--start_date` | | Дата, с которой считать (включительно) |
| `--end_date` | | Дата, до которой считать (не включая) |
| `--max-rows` | | Сколько строк показывать в блоке консольного отчёта, `0` — все |
| `--help` | `-h` | Справка |

Значение можно писать и через `=`, и отдельным аргументом: `--mode=async` то же самое,
что `--mode async`. Даты понимаются в нескольких форматах, включая `2022-01-01`,
`01.01.2022` и `1/1/2022`.

Примеры:

```bash
SalesAnalytics.Cli -m async -i sales_5000.csv
SalesAnalytics.Cli -m parallel -i sales_5000.csv --start_date=2022-01-01 --end_date=2023-01-01
SalesAnalytics.Cli -m console -i sales_5000.csv --max-rows=0
```

## Режимы

| Режим | Ввод-вывод | Расчёт | Зависимости |
| --- | --- | --- | --- |
| `console` | синхронный | последовательный | вручную |
| `file` | синхронный | последовательный | вручную |
| `async` | асинхронный | последовательный | вручную |
| `parallel` | синхронный | параллельный | вручную |
| `di` | синхронный | последовательный | контейнер |
| `full` | асинхронный | параллельный | контейнер |

В асинхронных режимах файл открывается с `FileOptions.Asynchronous`, строки читаются
через `ReadLineAsync`, JSON пишется через `JsonSerializer.SerializeAsync`.

В параллельных суммы по категориям считает `Parallel.ForEach` по диапазонам записей:
каждый поток копит свой промежуточный словарь, и уже готовые частичные суммы сливаются
в `ConcurrentDictionary`. Так синхронизация происходит раз на диапазон, а не на запись.
Статистика доставки сводится через `Interlocked`, остальные блоки — на PLINQ.

## Входной файл

CSV с заголовком и 12 колонками — `order_id`, `order_date`, `customer_id`,
`product_category`, `region`, `quantity`, `unit_price`, `discount`, `payment_method`,
`delivery_days`, `customer_rating`, `revenue`.

Разделитель определяется автоматически по заголовку: запятая, точка с запятой или
табуляция. Дробная часть — через точку, но для файлов с `;` принимается и запятая
(`373,65`). Пустые строки пропускаются, заголовок необязателен.

Считаются: сумма продаж по категориям, топ-4 категорий по количеству, средняя цена
по месяцам, топ-5 покупателей по рейтингу, время доставки и средняя скидка по
категориям в разрезе месяцев. Если заданы даты, всё считается по периоду
`[start_date; end_date)`.

## Архитектура

```
src/
  SalesAnalytics.Core/          домен, ничего не знает о способе запуска
    Models/                     Sale, AnalyticsReport, AnalyticsPeriod
    Abstractions/               ISaleParser, ICsvReader, ISaleLoader,
                                IAnalyticsService, IResultWriter, IResultWriterFactory
    Parsing/                    SaleParser, CsvReader, FileSaleLoader, CsvFormat
    Analytics/                  AnalyticsServiceBase + Linq/Parallel реализации
    Output/                     ConsoleResultWriter, JsonResultWriter, ResultWriterFactory
    Application/                AnalyticsPipeline
    DependencyInjection/        AddSalesAnalytics
    Exceptions/                 иерархия SalesAnalyticsException
  SalesAnalytics.Cli/           разбор аргументов, справка, композиционный корень
tests/
  SalesAnalytics.Tests/         xUnit + Moq
```

Весь сценарий сведён в `AnalyticsPipeline`: загрузить продажи, посчитать отчёт,
записать результат. Он не знает ни про командную строку, ни про конкретные реализации —
режим влияет только на то, что в него внедрено, поэтому порядок шагов во всех шести
режимах буквально один и тот же.

`AnalyticsServiceBase` держит общий каркас расчёта: фильтрацию по периоду, метаданные и
порядок блоков. Наследники переопределяют только способ вычисления конкретного блока.
Из-за этого последовательная и параллельная версии не могут разойтись по структуре
отчёта, а по значениям это проверяется тестом на большом наборе данных.

Чтение специально разделено надвое. `ICsvReader` работает с `TextReader`, а не с путём,
и отвечает только за обход строк и пропуск заголовка; за доступ к файлу отвечает
`ISaleLoader`. Благодаря этому разбор CSV тестируется через `StringReader`, без файлов
на диске. Похожая история с выводом: `IResultWriterFactory` нужен потому, что цель
записи известна только в рантайме, и заодно он проверяет каталог результата до чтения
и расчёта — незачем обрабатывать пять тысяч строк, если сохранять отчёт всё равно некуда.

Режимы `di` и `full` собираются через `IHost`, остальные — прямым созданием объектов;
доменный код в обоих случаях один и тот же.

Времена жизни в контейнере: парсер, читатель, загрузчик, служба расчёта и фабрика
писателей — `Singleton`, поскольку состояния между вызовами не держат (состояние разбора
живёт внутри вызова метода) и потокобезопасны. `AnalyticsPipeline` — `Transient`: это
объект одного запуска, он дешёвый, и отдельный экземпляр снимает вопрос о разделяемом
состоянии.

## Ошибки

Ожидаемые проблемы — нет файла, пустой файл, битая строка, недоступный каталог для
записи, неверные аргументы — наследуются от `SalesAnalyticsException`, печатаются в
`stderr` понятным текстом и дают код возврата `1`. Стек вызовов в консоль не попадает.
Сообщение о плохой строке содержит номер строки и имя колонки, например:

```
Ошибка: Ошибка разбора CSV в строке 3: колонка «order_date» содержит «ЧТО-ТО», ожидалась дата в формате ...
```

## Тесты

```bash
dotnet test
```

xUnit + Moq. Реальные файлы не используются — везде `StringReader`, `StringWriter`,
`MemoryStream` и моки. Покрыт разбор строк с граничными случаями (пустая строка, кривая
дата, не то число колонок, значения вне диапазона), обход файла, каждая аналитика на
маленьком наборе, регистрация и разрешение зависимостей, разбор аргументов и коды
возврата.

Асинхронность проверяется отдельно: обёртка над `TextReader` считает, каким способом
читались строки, а строгие моки в тестах конвейера подтверждают, что в асинхронном
режиме зовутся `LoadAsync`/`AnalyzeAsync`/`WriteAsync`, а синхронные версии не зовутся
вообще. Ещё есть тест, который сверяет параллельный расчёт с последовательным на
большом наборе — по сути проверка потокобезопасности агрегации.

## Пара замечаний по постановке

Сумму продаж по категориям считаю без скидки, как в примере ожидаемого вывода
(`373.65*7 + 311.28*3`). При этом в файле есть колонка `revenue` — выручка уже со
скидкой, поэтому в отчёт кладу обе величины.

В описании режимов сказано про «три аналитики», но в списке их шесть — сделал все шесть.

Консольный вывод по умолчанию урезан: блоки с разбивкой по месяцам на этих данных дают
сотни строк и вытесняют всё остальное из окна терминала. Показываются первые 24 строки
с пометкой, сколько скрыто; `--max-rows=0` печатает всё, в JSON и так всегда полный набор.

Покупатели в файле повторяются, поэтому рейтинг усредняется по всем заказам покупателя.
